# Remove HLL; add exact person-level bridge + `getPersonCounts()`

## Context

Today distinct-person counts are stored as **HyperLogLog (HLL++) sketches**
(`persons_hll_counts`) — a BigQuery-only feature, with a pure-R port in
`R/hllCount.R` used to merge them on SQLite. The scratchpad note
`.scratchpad/no_HLL_or_sketches.md` explains why this is a dead end: the target
feature is an **on-demand UpSet plot** of how patient sets overlap, filtered by
stratum. HLL cannot intersect sets, and every sketch family either loses the
cross-set person linkage or samples it — hopeless for the tiny (privacy-floor)
bars UpSet cares about. The measured data (strata median ~5 persons/row) makes
**exact** overlap cheap.

So: **remove HLL entirely** and replace it with an exact person-level bridge
table (`concept_id × stratum × person_id`), from which distinct-person counts and
set intersections are computed exactly — at build time (into `code_counts`) and
at request time (for the new `/getPersonCounts` endpoint). Exact `COUNT(DISTINCT
person_id)` is correct on both SQLite and BigQuery GoogleSQL, so person counts
work on every backend for the first time (today SQLite only ever had a `0`
placeholder).

Design decisions confirmed with the user:
- **No `person_counts_tree` output.** `code_counts`'s inclusion rule is "a
  concept has a row iff it has its own counts or at least one descendant with
  counts" (see `descendant_counts`'s `INNER JOIN atomic_code_counts cctosum` in
  `createCodeCountsTable.sql`) — the *exact same* filter `getConceptTree`'s tree
  SQL already applies (`concept_descendants_with_counts_or_descendance_counts`).
  So every node the tree shows already has a `code_counts` row; there is no
  intermediary/synthetic-node case to special-case. `person_counts`/
  `descendant_person_counts` per concept are already reachable via the existing
  `concepts` tibble (`getCodeCounts`/`getConceptsWithCodeCounts`, once Part C
  adds the two columns there) — `getPersonCounts` does not need to duplicate
  that as a tree output. It returns only `filter_person_counts` and
  `upset_person_counts`.
- **filter_person_counts** covers **sex, age, visit** dimensions only (year is a
  filter input, not a breakdown dimension).

New bridge table default name: **`stratified_persons`** (parallels
`stratified_code_counts`; one row per distinct `concept_id × stratum × person_id`).

## Part B — New person bridge table `stratified_persons` (BUILD)

One row per distinct `(concept_id, maps_to_concept_id, visit_group_concept_id,
calendar_year, gender_concept_id, age_decile, person_id)`. Same grain and same
strata as `stratified_code_counts`, but keeps `person_id` instead of collapsing
it to a count.

**New R function** `createStratifiedPersonsTable()` in a new file
`R/createStratifiedPersonsTable.R`, mirroring `createStratifiedCodeCountsTable.R`
(same domain tribble, same DROP+CREATE-empty-then-append-per-domain loop, same
`visitSourceGroupConceptIds` threading). Empty-table DDL columns: the six strata
keys + `person_id INTEGER` (no counts column). Give it the standard roxygen +
`@export`.

**New SQL** `inst/sql/{sql_server,bigquery}/appendToStratifiedPersonsTable.sql` —
structurally the `ccm` inner subquery of `appendToStratrifiedCodeCountsTable.sql`
(identical person/observation_period joins, strata derivation, visit-group
conditional, and WHERE), but the outer statement is
`INSERT ... SELECT DISTINCT person_id, concept_id, maps_to_concept_id,
visit_group_concept_id, calendar_year, gender_concept_id, age_decile` — no
`GROUP BY`/`COUNT`. Keep the `sql_server` file canonical; add `bigquery` only if
translation needs an override (mirror the existing pair's WHERE-clause
difference). Note the intentional structural duplication of the join block.

**Wire into orchestration** — `R/createCodeCountsTables.R`: after
`createStratifiedCodeCountsTable(...)` and **before** the `createCodeCountsTable.sql`
step (which will now read the bridge), call `createStratifiedPersonsTable(...)`.
Pass the new table name to the rollup render (below). Add a
`stratifiedPersonsTable = "stratified_persons"` default.

## Part C — `code_counts` gains `person_counts` + `descendant_person_counts` (BUILD)

Edit both `inst/sql/{sql_server,bigquery}/createCodeCountsTable.sql`:

1. **DDL** — add `person_counts int, descendant_person_counts int` to the
   `CREATE TABLE`.
2. **Atomic person counts** — new CTE reading the **bridge**, mirroring
   `atomic_code_counts`' two branches but with distinct persons:
   ```
   atomic_person_bridge AS (            -- person-level, keyed by concept
     SELECT concept_id AS concept_id, person_id FROM @stratifiedPersonsTable
       WHERE concept_id != 0
     UNION ALL
     SELECT maps_to_concept_id AS concept_id, person_id FROM @stratifiedPersonsTable
       WHERE concept_id != maps_to_concept_id
   ),
   atomic_person_counts AS (
     SELECT concept_id, COUNT(DISTINCT person_id) AS person_counts
     FROM atomic_person_bridge GROUP BY concept_id
   )
   ```
   (sql_server keeps its `concept_id != 0` guard on branch 1; bigquery omits it,
   matching the existing record-side asymmetry.)
3. **Descendant person counts** — cannot sum atomic counts (double-counts persons
   under multiple descendants). Compute distinct persons over the descendant set
   via `temp_concept_ancestor` joined to `atomic_person_bridge`:
   ```
   descendant_person_counts AS (
     SELECT ca.ancestor_concept_id AS concept_id,
            COUNT(DISTINCT b.person_id) AS descendant_person_counts
     FROM temp_concept_ancestor ca
     INNER JOIN atomic_person_bridge b ON ca.descendant_concept_id = b.concept_id
     GROUP BY ca.ancestor_concept_id
   )
   ```
4. **Final SELECT** — LEFT JOIN `atomic_person_counts` and
   `descendant_person_counts` onto the existing `descendant_counts` result on
   `concept_id`; `COALESCE(...,0)` and CAST to BIGINT alongside the four existing
   columns.

`getConceptsWithCodeCounts()` (`R/getConceptsWithCodeCounts.R`) already does
`cc.*`-style explicit column selection — add `cc.person_counts,
cc.descendant_person_counts` there so the catalogue exposes them. **Required**,
not optional: this is now the only path by which per-concept person counts reach
a client (see Part E — `getPersonCounts` no longer returns a tree of its own).
Confirm it doesn't break the `/getListOfConcepts` subset endpoint, which selects
its own explicit column list and stays as-is (pc/dpc are additive columns on the
tibble, not surfaced by that endpoint unless asked for). **`getCodeCounts` must
NOT return person counts** — leave its `stratified_code_counts` output
unchanged; its `concepts` tibble will pick up `person_counts`/
`descendant_person_counts` for free via `getConceptsWithCodeCounts_memoise`.

## Part E — `getPersonCounts()` + `/getPersonCounts` endpoint

**New file** `R/getPersonCounts.R`:

```
getPersonCounts(CDMdbHandler, conceptId,
                level = NULL,                 # max tree depth; NULL = full depth
                sexStratum = NULL, ageStratum = NULL,
                yearStratum = NULL, visitStratum = NULL,  # NULL/empty = all
                codeCountsTable = "code_counts")
```
camelCase per STYLE.md; validate with `checkmate` like the other getters.

Returns `list(filter_person_counts, upset_person_counts)` — two tibbles, not
three. Per-concept `person_counts`/`descendant_person_counts` are already
available via `getCodeCounts()$concepts` (Part C), so this getter is scoped to
the two things that table can't answer: stratum breakdowns and set overlaps.

Steps:
1. `getConceptTree_memoise(...)` → family tree + `conceptIdsToGetCounts`.
   Derive the depth of each node from `levels`; apply `level` cutoff to get the
   "over-level" node set (nodes at depth ≤ level; NULL ⇒ all). Build mappings the
   same way `getCodeCounts` does to include mapped concepts.
2. **`filter_person_counts`** (columns: `filter` ∈ {sex, age, visit}, `stratum`,
   `person_counts`): from the bridge restricted to the tree's concept ids, for
   **all** persons in the tree regardless of `level`, three `COUNT(DISTINCT
   person_id)` aggregations grouped by `gender_concept_id`, by `age_decile`, by
   `visit_group_concept_id`, unioned long-format. (No year dimension.)
3. **`upset_person_counts`** (columns: `group` = over-level concept ids joined by
   `-`, `person_counts`): exact UpSet exclusive regions. From the bridge, filtered
   to over-level concept ids **and** the requested strata
   (sex/age/year/visit filters applied as `IN (...)` when non-empty), derive each
   person's membership set over those concepts, build the sorted-`-`-joined group
   key, and `COUNT(DISTINCT person_id)` per key. Compute in SQL where practical
   (`GROUP BY person_id` → membership → outer group-by), else assemble the group
   key in R from a person×concept bridge pull; keep the result set small
   (only region counts cross the wire).

Add `getPersonCounts_memoise <- memoise::memoise(getPersonCounts, omit_args =
"CDMdbHandler")`.

**Endpoint** — `inst/plumber/plumber.R`, mirroring the `/getCodeCounts` block:
```
#* @get /getPersonCounts
function(res, conceptId=0L, level=NULL,
         sexStratum=NULL, ageStratum=NULL, yearStratum=NULL, visitStratum=NULL) { ... }
```
Coerce `conceptId`/`level` to integer; parse each `*Stratum` from a
comma-separated string into an integer vector (empty ⇒ NULL). Validate
(`is.na` → 400 with `jsonlite::unbox`), delegate to `getPersonCounts_memoise`
inside `tryCatch` → 400 on error. Register in the STRUCTURE.md endpoint table.

## Notes / caveats
- **Governance:** `stratified_persons` is pseudonymous person-level data in the
  results schema (the scratchpad note flags this) and its small-cell counts need
  the usual suppression downstream. In scope per the user's design; called out
  so it isn't a surprise.
- Structural duplication between `appendToStratrifiedCodeCountsTable.sql` and
  `appendToStratifiedPersonsTable.sql` (shared join block) is intentional —
  SqlRender has no clean include mechanism.
